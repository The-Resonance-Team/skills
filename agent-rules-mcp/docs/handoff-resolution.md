# Agent rules MCP handoff resolution

This document records the decisions from the grill-with-docs review of the
Cloudflare Free optimisation handoff and their implementation status.

## Settled scope

1. The Worker submits an approved rule patch as a draft pull request. Review,
   edits, and merge decisions remain in GitHub. PR-status tracking in the approval
   dashboard is out of scope.
2. Rule publication follows a successful rebuild and deployment from the
   repository. There is no separate live-refresh interval or freshness target.
3. Expired dashboard access can be renewed after authorization. Renewal preserves
   the same rule patch proposals and their decision history. Link expiry must not
   silently delete proposals.
4. Workers Free remains a hard limit. Do not enable Paid-only features, push to
   `main`, merge automatically, or deploy the separate Dynamic Worker experiment.
5. Approval, denial, and access renewal require Cloudflare Access sign-in and
   explicit reviewer authorization. Record the reviewer identity. A proposal link
   alone does not permit a decision.
6. Pending proposals have a 30-day review window. Preserve history for 90 days
   after a final outcome. Preserve uncertain submission attempts until resolved.
   Show proposal expiry explicitly and keep it separate from access expiry.
7. An unused approval is valid for 24 hours. After expiry, a reviewer can approve
   the same unchanged proposal again. Preserve the previous decision. Access
   renewal does not extend an approval or reset a used approval.
8. Before submission, compare the target file with the reviewed original.
   Unrelated changes to `main` do not invalidate approval. A changed target file
   requires a refreshed proposal and human review. The React dashboard uses
   `@pierre/diffs` plus a JSDiff-generated plain unified patch.
9. An accepted submission must finish independently of the client connection.
   Repeated requests return the same proposal or submission result. Recover an
   uncertain attempt by checking its matching GitHub branch and pull request,
   ending recovery once the submission outcome is known. Create at most one draft
   pull request per proposal.
10. Keep Workers AI and local ranking for the 29-entry catalog. Bound query-vector
    caching. Return explicitly labelled lexical results when inference fails or
    reaches its Free quota. Preserve retrieval scope and check recall before
    release. FTS5 and Vectorize require a measured benefit before adoption.
11. Reviewer sign-in protects all dashboard data, including proposal diffs and
    history. Authorized reviewers can open the stable repository board and renew
    access without the original proposal link.
12. A maintainer regenerates the catalog and genuine embedding cache on the draft
    branch before marking the pull request ready. Provide a complete trusted
    command with credentials kept out of PR scripts. PR checks validate source,
    snapshot consistency, and recall before merge. Trusted CD rebuilds and checks
    again before publishing.
13. Use `@pierre/diffs@1.7.1` for React file-diff review, loaded when needed.
    Default to a wrapped unified view with full context, with Split available on
    wide layouts. Offer a plain unified-text alternative generated by JSDiff in
    Astryx CodeBlock. Remove the handwritten diff algorithm. Preserve whitespace
    and final-newline changes; keep Markdown as source text during review.
14. Extend the existing Durable Object with persistent submission phases and one
    alarm schedule shared by submission, recovery, and retention cleanup. Add one
    hourly Cron repair pass for stranded due work or a lost wake-up. It does not
    poll known PR status or refresh the catalog. Do not add Workflows or Queues
    for this implementation.
15. Initially authorize only the current Cloudflare operator as a reviewer, using
    an explicit verified-email allowlist in the Worker. Reuse the existing Access
    OIDC app for authentication and keep reviewer authorization separate from
    MCP scopes. Add team reviewers only through an explicit allowlist change.

## Established engineering facts

- Pin both Worker packages to published stable `bun@1.4.5` and restore
  `bun-version-file: ${{ inputs.package }}/package.json` in the reusable workflow.
  Keep the existing team rule. Passing Ubuntu CI already used stable 1.4.5;
  local 1.4.6 is a canary without matching stable Linux release assets.
- Keep `oxlint@1.95.0`: native Bun lint is canary-only in the verified stable
  release. This task does not require a team-wide toolchain rule change.
- Reuse the existing Access OIDC app and callback for browser reviewer sign-in,
  with separate browser-bound transaction state and a secure reviewer credential.
  Do not issue an MCP grant in the reviewer callback or trust posted identity.
- Record reviewer issuer, subject, and email snapshot on decisions. Keep the MCP
  client and authorizing subject distinct. Preserve current MCP OAuth subjects.
- Current authenticated MCP reads work, but the active Worker predates the
  branch's `PATCHES` binding. Green PR checks do not establish a deployed version
  or a successful CD run.
- The existing deploy workflow rebuilds before checking and deploying. The
  current rule-only PR path needs the chosen draft regeneration step before its
  required checks can pass.
- GitHub exposes no create-PR idempotency key. An unknown response followed by an
  empty search is not proof that the write failed. Persist the attempt before
  sending it, recover matching results, and preserve uncertainty when the
  original outcome cannot be established. Do not issue a blind second PR write.
- Compare the reviewed target at a pinned base commit. Main can still advance
  during external calls. Keep the approved diff and base identity intact; later
  source changes remain subject to GitHub review, with no automatic merge.
- The serving account's dashboard confirms Workers Free as its current plan.
  Complete Worker/schedule enumeration found one Worker and zero Cron triggers;
  the selected repair pass uses one of the five Free account slots.
- Authenticated Access reads confirm that the configured SaaS app's client ID
  matches the Worker and its production `/callback` URL is registered. Its
  current policy allows Everyone and its sole identity provider is email
  one-time PIN. The selected Worker reviewer allowlist is therefore required;
  sign-in alone is insufficient.
- A complete read-only prefix inventory found one legacy `patch:` record, one
  expiring `approval:` record, and zero `dash:` records in `OAUTH_KV`. No proposal
  contents, approval values, or capability-bearing key names were printed.
- The current operator identity was verified in the signed-in Cloudflare user
  menu. Configure that verified email in the reviewer allowlist without copying
  personal identity data into this design document.

## Legacy storage migration

Historical source at `ed4f27d1d8f66df825466b4a8526c2422d4f176d` stored proposals
and approvals in `OAUTH_KV`. The Durable Object class migration only creates the
new store; it does not import those records.

- Legacy `patch:` records have no storage TTL. Legacy `approval:` records expire
  after 24 hours; record their surviving evidence promptly during migration.
  Dashboard records have their own expiry and are unnecessary for rebuilding
  board membership.
- Use a bounded, resumable one-time importer. Pause legacy mutations during the
  transition, account for old in-flight requests and KV propagation, and follow
  every list cursor. Do not keep permanent dual writers.
- Preserve original IDs, content, digests, timestamps, decision evidence, and
  provenance. Import approval records independently of the proposal's current
  approval ID. Missing, malformed, or conflicting records require reconciliation.
- A legacy approved proposal without a PR URL may already have attempted a
  submission: the old code did not persist uncertainty before calling GitHub.
  Reconcile it before allowing a new submission. Preserve used or unknown
  evidence and existing PR URLs.
- Historical decisions have no reviewer identity. Preserve that fact. A fresh
  authorized decision is required for a new submission after reconciliation;
  renewal and migration cannot create new approval authority.
- Verify aggregate imported and unresolved counts after quiescence and KV
  propagation. A single empty scan or elapsed time alone does not prove import
  completion. Leave source KV records untouched during the verification window;
  never clear the shared OAuth namespace.
- Apply 30/90-day retention after classification, using original or explicitly
  conservative timestamps. Unresolved attempts remain exempt from cleanup.

## Implementation sequence

1. Correct toolchain selection and workflow guards. Keep published stable Bun
   1.4.5, version-file pinning, and pinned Oxlint consistent.
2. Establish the stable repository board, decision history, and safe storage
   migration. Preserve known submissions and uncertain attempts. Historical
   approvals without authenticated reviewer attribution need fresh review before
   a new submission; do not invent identities or reset used permission.
3. Reuse Access OIDC for a separate reviewer browser credential, bound login
   transactions, and server-derived identity. Protect all dashboard data and
   mutations. Keep MCP authentication and its read-only bearer path intact.
4. Implement access renewal, 30/90-day retention, 24-hour approval validity, and
   explicit proposal/approval expiry. Preserve decision results after the final
   pending proposal is decided.
5. Add pinned target-file verification, repeatable proposal/submission results,
   and persistent submission phases. Finish accepted work independently of the
   requesting client. Recover its original branch/PR before any further write.
   Use the selected shared DO alarm and hourly repair Cron for progress and
   retention cleanup.
6. Replace handwritten diff output with the selected deferred Pierre viewer and
   a JSDiff-generated text alternative. Keep the surrounding controls and theme
   in Astryx, with exact source text available throughout review.
7. Bound vector caching and expose semantic versus lexical-fallback mode. Keep
   current retrieval scope and verify the same recall cases before release.
8. Provide the trusted draft-regeneration command. Read proposed Markdown as
   data, execute trusted builder/inference code, and keep credentials away from
   PR scripts. Update generated files on the draft branch and check the genuine
   snapshot before ready-for-review.
9. Update implementation docs and deployment annotations with the built commit,
   source digest, and artifact digest. Check the active version after deployment;
   an uploaded version or a green PR run alone is insufficient.
10. Run the package, workflow, UI, and failure-path checks. Deploy the revised
    rules Worker on Free, perform the human-reviewed draft-PR smoke test, close
    the test PR, and record concrete outcomes for every original handoff item.

## Design tree

```text
Workers Free; human approval; no push to main or automatic merge
├── Patch submission: Worker opens a draft PR
│   ├── PR-status tracking: excluded
│   ├── Changed target: refreshed proposal and human review; React diff library
│   ├── Approval: 24 hours; fresh review can renew an unused approval
│   ├── Retries: finish independently and recover one PR per proposal
│   ├── Diff: Pierre plus a JSDiff-generated plain unified-text view
│   ├── Execution: DO phases, shared alarms, hourly repair Cron
│   └── Verification: real human-approved submission and closure
├── Rule publication: successful rebuild and deploy
│   ├── Live catalog refresh: excluded
│   ├── Draft review: trusted catalog regeneration before ready-for-review
│   └── Toolchain: stable Bun 1.4.5 from each package manifest
├── Dashboard access: renewable without losing proposals or history
│   ├── Authority: signed-in Access reviewer, recorded with each decision
│   ├── Retention: 30 days pending; 90 days final; uncertain attempts preserved
│   ├── Visibility: reviewer sign-in for all proposal data and history
│   ├── Reviewers: current operator only, explicitly allowlisted
│   └── Migration: preserve and reconcile surviving live KV records
└── Free-tier optimisation: adopt features with a demonstrated benefit
    ├── Search: local vectors, bounded cache, visible lexical fallback
    └── Budget: Workers Free verified; repair uses one of five available slots
```

## Acceptance evidence

The implementation must demonstrate these outcomes before the handoff is closed:

- An unauthenticated or unauthorized caller cannot approve, deny, or renew review
  access. Each successful decision identifies its reviewer.
- Renewing expired access restores the same proposals and history. Completing
  the last review does not make the recorded decision or submission result
  unrecoverable.
- Access renewal does not revive an expired or used approval. A fresh review of
  an unchanged proposal creates a separate recorded decision.
- Pending expiry and final-history retention follow the agreed periods. Cleanup
  does not remove an unresolved submission.
- A changed target file prevents submission under the old approval. The new diff
  requires review. An unrelated source commit still permits submission.
- Repeated proposal and submission requests return the original result.
  Concurrent requests, client disconnects, GitHub response loss, and a failed
  final storage update cannot create a second draft pull request.
- Source changes reach the MCP through the existing build and deployment path.
  Failed refresh or deployment does not publish an invalid catalog.
- Adopted Cloudflare services are available on Workers Free. Their use and
  failure behavior stay within the documented limits.
- The package-manager declarations and CI select the same published stable Bun
  version and pass the repository checks.
- One real proposal is reviewed by a human on the deployed Worker, submitted as a
  draft pull request, checked for the expected branch and title, and closed.
  Record the pull-request URL and outcome. Do not merge it.
